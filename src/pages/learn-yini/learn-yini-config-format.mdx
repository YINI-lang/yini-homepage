## 1. Sections

Sections group related configuration settings under a named header.

A section starts with a _section marker_, usually `^`, followed by the section name.

```yini
^ App
title = "AppName"
```

Here, `title` belongs to the `App` section.

> `^` is the recommended section marker. `§` may be used as a Unicode-based alternative.

> See section 9 for more advanced marker and naming options.

---

## 2. Keys and Values

Each configuration setting is written as a **key-value pair**, separated by `=`:

```yini
maxConnections = 100
enableLogging  = true
appName        = "My App"
```

The text before `=` is the key. The text after `=` is the value.

Values can be different types, such as strings, numbers, booleans, null, lists (arrays), and inline objects:

```yini
title    = "Demo App"
port     = 8080
debug    = true
theme    = null
colors   = ["red", "green", "blue"]
database = { host: "localhost", port: 5432 }
```

Use backticks for section or key names that contain spaces, punctuation, or other characters that are not allowed in plain names:

```yini
user id = 1      # ❌ Invalid
`user id` = 1    # ✅ Valid

api.version = "v1"   # ❌ Invalid
`api.version` = "v1" # ✅ Valid

1stUser = "Alice"    # ❌ Invalid
`1stUser` = "Alice"  # ✅ Valid
```

> See section 9 for more advanced naming rules.

## 3. Values

Values define the actual configuration data (settings).

Compare strings, booleans, and numbers in the
[value literal examples](/learn-yini/examples/values).

In YINI, values can be several common data types:

### Strings

Strings are text values and are written with quotes.

You can use either single (`'`) or double quotes (`"`):

```yini
name = "Alice"
city = 'Gothenburg'
```

Strings in YINI are raw by default. This means backslashes are treated as normal text, which is useful for file paths:

```yini
path = "C:\Users\john\Documents"
```

If you need escape sequences such as `\n` for a newline, use an Escaped String by prefixing the string with `E` or `e`:

```yini
message = E"Server started\nReady."
```

For longer multi-line text, use _triple-quoted strings_:

```yini
description = """
This is a longer text.
It can span multiple lines.
"""
```

The older `C` and `c` prefixes remain valid in both modes, but are deprecated in RC7. Use `E` or `e` for new documents, including escaped triple-quoted strings such as `E"""..."""`.

Triple-quoted strings keep their whitespace and line breaks, with source LF, CRLF, and CR line endings normalized to LF.

For multiline commands or scripts, RC7 also defines Command Strings:

```yini
build = command"""
    npm ci
    npm run build
"""
```

This produces the ordinary string `npm ci\nnpm run build`. YINI does not execute it. The lowercase `command` prefix requires a line break after the opening delimiter, and the closing delimiter must be alone on its line. Structural indentation is removed; backslashes stay literal.

### String Concatenation

Use `+` to join strings. A concatenation must start with a string literal. In strict mode, every operand must be a string literal. Lenient mode also allows later number, boolean, and null operands:

```yini
title = "YINI: " + "Readable config"
portLabel = "port-" + 8080  // Lenient mode only.
exponent = "scale-" + 1e3  // "scale-1e3", not "scale-1000".
```

YINI does not perform numeric addition. A line break may appear after `+`, but not before it. In lenient concatenation, decimal numbers retain their normalized source spelling; non-decimal integers become base-10 text. See the [scalar conversion rules](/refs/specification#67-scalar-conversion-in-lenient-concatenation).

### Numbers

Numbers can be integers, decimals, negative numbers, or numbers with visual separators:

```yini
port = 8080
price = 19.99
offset = -10
population = 10_000_000
```

Underscores can make large numbers easier to read. `10_000_000` has the same value as `10000000`.

Use `0b` for binary numbers, for example `0b1010`. The older `%` prefix remains valid in both modes but is deprecated in RC7.

### Booleans

Booleans represent true/false values:

```yini
debug = true
enabled = false
```

YINI also accepts boolean-like words such as `on`, `off`, `yes`, and `no`.

### Null

Use `null` when a value is intentionally empty or not set:

```yini
theme = null
```

In lenient mode, a blank root-level or section-level value after `=` becomes `null` and must produce a warning:

```yini
theme =
```

Strict mode rejects blank values. Missing values inside lists or inline objects are errors in both modes; use explicit `null` instead.

### Lists

Lists store multiple values under one key:

```yini
colors = ["red", "green", "blue"]
```

Lists are explained in section 6.

### Inline Objects

Inline objects group small related values inside one value:

```yini
database = { host: "localhost", port: 5432 }
```

Inline objects are explained in section 7.

## 4. Comments

Comments help document configuration files and are ignored by the parser.

YINI supports several comment styles:

```yini
// This is a line comment
timeout = 30  // inline comment

# This is also a line comment
interval = 30  # Inline comment

/* Block comment spanning
   multiple lines */

; Full line comment
```

`//`, `#`, and block comments can be used on their own line or inline after a setting.

```yini
timeout = 30  // Good
interval = 30 # Good
```

The `;` comment style is only for full-line comments. It must be the first non-whitespace character on the line.

```yini
; Good ✅
timeout = 30 ; Invalid ❌
```

> Outside string literals and backticked identifiers, `#` always starts a comment. No whitespace is required before or after it, so `color = #336699` leaves `color` without a value: `null` with a warning in lenient mode, or an error in strict mode. Write a hex number as `0x336699` or `hex:336699`.

💡**Tip:** You can use any comment style in your file.
For best readability, try to stick to one style per file.

### Disabled Lines

Disabled lines let you temporarily turn off a configuration line without deleting it.

Prefix any valid line with `--` to skip it entirely:

```yini
--maxRetries = 5
```

💡 This can be useful while testing or changing configuration values. Disabled lines are for temporarily turning off configuration; comments are for notes meant for humans.

## 5. Nested Sections

Nested sections let you group configuration inside other sections.

Use more `^` markers to create deeper section levels:

```yini
^ Server
host = "localhost"

^^ Database
name = "app_db"
port = 5432
```

Here, `Database` belongs inside `Server`.

You can go deeper by adding more `^` markers:

```yini
^ App
^^ Logging
^^^ File
path = "logs/app.log"
```

This creates the following structure:

```js
{
    App: {
        Logging: {
            File: {
                path: 'logs/app.log'
            }
        }
    }
}
```

Indentation is optional. YINI uses the section markers, not indentation, to understand the structure.

```yini
^ App
    ^^ Logging
        ^^^ File
        path = "logs/app.log"
```

This means the same thing as the previous example. The indentation is only for readability.

Compare different formatting styles in the
[indentation examples](/learn-yini/examples/indentation).

To return to a top-level section, use a single `^` again:

```yini
# Level 1
^ App
name = "Demo"

# Level 2
^^ Logging
level = "info"

# Back at level 1 again
^ Server
port = 8080
```

> See section 9 for more advanced marker and naming options.

## 6. Data Type: Lists

Lists let you store multiple values under a single key.

In YINI, a list value is assigned to a key with `=`, and the list itself is written inside square brackets `[ ... ]`.

```yini
// Single-line list
colors = ["red", "green", "blue"]

// Multi-line list
numbers = [
    10,
    20,
    30
]
```

Lists can contain different supported value types, such as strings, numbers, booleans, null, inline objects/maps, and even other lists.

```yini
mixed = [
    "Pear",
    42,
    true,
    null,
    { name: "Cherry", color: "red" },
    ["nested", "list"]
]
```

> You can use either single or double quotes for string values in YINI.
>
> In lenient mode, a trailing comma after the last list item is allowed. In strict mode, it is not.

## 7. Data Type: Inline Objects

Inline objects let you group related values together inside a single value.

They are written inside curly braces `{ ... }`, with each item written as `key: value`.

```yini
user = { name: "Alice", role: "admin" }
```

This creates an object-like structure:

```js
{
    user: {
        name: "Alice",
        role: "admin"
    }
}
```

Inline objects are useful for small grouped values that belong together.

```yini
server = { host: "localhost", port: 8080 }
theme = { name: "dark", contrast: "high" }
```

Inline objects can contain supported value types such as strings, numbers, booleans, null, lists, and other inline objects.

```yini
profile = {
    name: "Alice",
    active: true,
    tags: ["admin", "editor"],
    address: { city: "Gothenburg", country: "Sweden" }
}
```

For larger or more important structures, nested sections are usually easier to read.

```yini
^ User
name = "Alice"
role = "admin"
```

> In strict mode, inline object entries must use `key: value`; `key = value` is invalid inside inline objects. Lenient parsers must accept both separators, including mixed separators in one object. Prefer the canonical `key: value` form.

## 8. Lenient vs. Strict

YINI can be parsed in two modes: **lenient** and **strict**.

Lenient mode is the default. It is more forgiving and is useful while writing, editing, or experimenting with configuration files.

Strict mode is more careful. It is useful when you want stronger validation, clearer errors, and more predictable files in tools, CI, or production-like environments.

- Lenient mode = easier while editing
- Strict mode = stricter validation

### Optional Mode Declaration

A YINI file may declare the mode it expects:

```yini
@yini lenient
```

```yini
@yini strict
```

This tells readers which mode the file is meant for.

It does not switch the parser mode by itself. The parser, CLI option, API call, or application still chooses whether to use lenient or strict mode.

If the file declares one mode but the parser uses another, the parser reports a mode mismatch. `@yini strict` parsed in lenient mode must be rejected. `@yini lenient` parsed in strict mode produces a warning; the document must still pass all strict-mode checks.

### Duplicate Names and Root-Level Values

Duplicate section names under the same parent are errors in both modes. Sections cannot be reopened or merged by repeating their header.

Duplicate keys are errors in strict mode. In lenient mode, the first value is kept and later duplicates are ignored with a warning. A key and a child section cannot share a name under the same parent in either mode.

Lenient mode allows key-value pairs before the first section. They appear directly on the document root alongside top-level sections, without an implicit `base` object:

```yini
title = "Demo"
^ Server
port = 8080
```

```json
{ "title": "Demo", "Server": { "port": 8080 } }
```

### Example Difference

Some things that may be accepted in lenient mode are rejected in strict mode.

For example, a trailing comma in a list is allowed in lenient mode, but not in strict mode:

```yini
colors = [
    "red",
    "green",
    "blue",
]
```

In lenient mode, this can be accepted.

In strict mode, the last comma after `"blue"` is an error.

### Document Terminator (strict mode)

The document terminator marks the explicit end of a YINI file.

The `/END` marker is optional in lenient mode (the default) and required in strict mode.

End a file explicitly with:

```yini
^ App
title = "MyTitle"

/END    // Required in strict mode, optional in lenient mode.
```

In strict mode, `/END` makes it clear where the configuration document ends.

Only comments and whitespace may follow `/END`. A complete final line does not need a trailing newline in either mode, including a strict document ending immediately after `/END`.

Strict mode also requires exactly one explicit top-level section. Any other sections must be nested inside that top-level section, and loose top-level key-value pairs are not allowed.

```yini
@yini strict

^ App
name = "MyApp"

^^ Database
host = "db.local"

/END
```

### When to Use Each Mode

Use **lenient mode** when you want a more forgiving experience while editing or trying YINI.

Use **strict mode** when you want stronger checks, especially for shared configuration files, automated tests, CI, or parser conformance.

- Use lenient mode while writing.
- Use strict mode when validating.

## 9. Advanced: Section Markers and Naming

Most YINI files only need the standard section marker `^` and simple names.

This section shows a few advanced options that are useful in special cases.

### Alternative Section Marker

The recommended section marker is `^`.

```yini
^ App
title = "My App"
```

If `^` causes problems in a specific environment, `§` may be used as a Unicode-based alternative.

```yini
§ App
title = "My App"
```

For most files, prefer `^`.

> Note: YINI also supports `>` and `<` as ASCII fallback markers, but they are not recommended for normal files.

### Backticked Names

Use backticks for section names or key names that contain spaces, punctuation, or other characters that are not allowed in plain names.

```yini
^ `User Settings`
`user id` = 42
`api.version` = "v1"
```

Without backticks, names like `user id` and `api.version` are not valid plain names.

Inside backticked names, use a backslash before a backtick or another backslash to include that character literally. These are the only supported escapes in identifiers. Invalid names are errors in both modes.

### Deep Section Levels

For normal nesting, use repeated `^` markers:

```yini
^ App
^^ Logging
^^^ File
```

Repeated section markers are supported up to level 9.

For deeper repeated section markers, underscores can visually group the
markers and make the section depth easier to count. The underscores do not
change the depth. Establish the parent levels first, and use distinct names for siblings:

```yini
^ App
^^ Services
^^^ API
^^^^ Routes
^^^^^ Options
^^^^^^ Settings        # Level 6.
^^^_^^^ GroupedSettings # Also level 6; a different sibling section.
```

For deeper nesting, use numeric shorthand:

```yini
^ App
^^ Services
^^^ API
^^^^ Routes
^^^^^ Options
^^^^^^ Settings
^^^^^^^ Advanced
^^^^^^^^ Details
^^^^^^^^^ DeepSection  # Level 9
^10 VeryDeep           # Level 10
```

Numeric shorthand requires a space or tab after the number. These header fragments assume a depth-9 parent has already been established:

```yini
^10 VeryDeep     # ✅ Valid
^10VeryDeep      # ❌ Invalid
```

### More Advanced Features

YINI also supports additional number notations, string types, escaping rules, parser modes, and validation rules.

For full details, see the [YINI Specification](/refs/specification).

## 10. Complete Example

This example combines the most common YINI features in a single configuration file.

```yini
@yini       # Optional marker to identify the file as YINI.

^ App
name    = "MyApp"
version = "1.0.0"
debug   = false  // Turn on for debugging.

^^ Database
host     = "db.local"
port     = 5432

// Below line is temporarily disabled.
--maxConnections = 100

users = ["alice", "bob", "carol"]
```

This creates an `App` section with a nested Database section.

> This example uses lenient mode (the default), so `/END` is not required.

See how these features fit together in
[common real-world configurations](/learn-yini/examples/common).
