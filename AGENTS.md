## Project Overview

- **Name:** yini-homepage
- **Purpose:** Official public website for YINI and yini-lang.org.
- **Language/runtime:** TypeScript 5.x on Node.js >=20.
- **Package manager:** npm, with `package-lock.json`.
- **Framework/stack:** Astro 6, React 18 islands/components, MDX, Tailwind CSS 4, ESLint, Prettier.
- **Module format:** ESM (`"type": "module"` in `package.json`).
- **Monorepo:** No.

The site presents the YINI format, specification, guides, examples, parser/tooling pages, and downloadable/static assets. Part of the site configuration is authored in YINI and generated to JSON before development and production builds.

## Commands

Install dependencies:

```bash
npm install
```

Generate JSON from the YINI site config:

```bash
npm run gen:config
```

Start local development:

```bash
npm run dev
```


## Generated Files and Config

- `site-config.yini` is the source of truth for site configuration.
- `src/config/site-config.json` is generated by `npm run gen:config`.
- `predev` and `prebuild` run config generation automatically.
- `npm run gen:config` invokes `npx yini-cli`. If config generation fails
  because the CLI cannot be resolved, report that clearly rather than replacing
  the generation flow casually.
- If changing `site-config.yini`, run `npm run gen:config` and include the resulting `src/config/site-config.json` change when the generated output is part of the requested work.
- Do not hand-edit generated output such as `dist/`, `.astro/`, or `src/config/site-config.json` unless the task explicitly requires generated artifacts.
- Treat `src/config/conf.ts.bak` and `src/config/config.yini.old` as historical backup files; do not update them unless explicitly asked.

## Code Style

Follow the existing style of the repository.

General rules:
- Prefer clear, simple, maintainable code.
- Prefer small, focused changes.
- Do not rewrite unrelated code.
- Do not reformat files unnecessarily.
- Keep public URLs and page routes stable unless the task explicitly asks for a route change.
- Keep public APIs stable unless the task explicitly asks for an API change.
- Add or update validation when behavior changes, using the available lint/typecheck/build workflow.
- Prefer explicit, readable logic over clever or overly compact code.
- Preserve existing naming conventions, file layout, and architectural patterns.
- Keep browser-only code compatible with Astro's server-side rendering model.
- Use existing Node API shims in `src/shims/` instead of adding browser polyfills casually.

Formatting conventions from the repo:
- 4-space indentation.
- Single quotes.
- No semicolons.
- Trailing commas where Prettier adds them.
- 80-column Prettier print width.
- Import ordering is handled by the configured Prettier plugins.
- When editing Markdown files, if a line introduces a bulleted list and ends
  with a colon (`:`), place the first bullet immediately on the next line. Do
  not insert a blank line between the introductory line and the first bullet.

## `yini-homepage`-Specific YINI Notes

The YINI format values clarity, readability, predictability, explicit structure, and deterministic parsing.

This repository contains the public website for the YINI configuration format.

The website should present YINI as clear, practical, technically credible, and aligned with the current specification. Avoid hype, exaggerated claims, or unsupported statements about maturity, adoption, benchmarks, or ecosystem support.

### Content and Tone

* Use precise, factual, non-salesy wording.
* Emphasize clarity, readability, explicit structure, deterministic parsing, and human-friendly syntax.
* Keep explanations concise and approachable.
* Do not invent features, parser behavior, syntax, adoption claims, or implementation status.

### Specification Accuracy

Website examples and explanations must match the current YINI specification.

Pay special attention to syntax and behavior related to:

* Section markers.
* Strict vs. lenient mode.
* Comments.
* Strings and escape handling.
* String concatenation.
* Inline objects and lists.
* Duplicate keys and sections.
* Document terminator behavior.
* Removed or reserved syntax.

Do not add examples unless they are valid according to the current specification, or clearly marked as invalid examples.

### Website Changes

Preserve the existing structure, navigation, links, analytics, metadata, sitemap, robots, and SEO-related code unless the task explicitly requires changes.

When changing navigation, check both top navigation and side navigation for consistency.

### Analytics

Analytics must never be tracked during local development or preview. Always ensure that site statistics and analytics services, such as Plausible, Umami, Google Analytics, and similar tracking scripts, are loaded only on the production site (`yini-lang.org` / `www.yini-lang.org`) and never when browsing locally, including via `localhost`, loopback/LAN addresses, or when serving a production
build locally with `npm run preview`.

### Visual Style

Preserve the YINI visual identity.

Keep the design clean, readable, and documentation-focused. Avoid visual clutter, excessive animation, or styling that makes technical content harder to read.

### Before Finishing

For meaningful changes, summarize changed pages/components, syntax example changes, navigation or link changes, checks run, and remaining risks.
